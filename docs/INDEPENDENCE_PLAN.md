# DeskForge 独立化执行计划

> 2026-10-06 基于当前仓库 `ad95e8d` 的审查记录。本文是工程与发布计划，不替代正式的版权和商标法律意见。

## 先定义终点

“自己的程序”有三个不同层次，需要分别验收：

1. **产品独立**：有自己的用户、场景、交互、品牌、发布与维护路线。可以继续使用 MIT 许可的上游代码，并履行署名和许可文本保留义务。这只是过渡状态。
2. **代码独立**：未来发布物不再包含 OpenWorkbuddy 的代码或基于其代码改写的部分。需要按独立需求和接口重新实现、审计来源，并保留迁移期间的证据。**用户选择这一层作为最终目标**；达到这一层并经来源审查后，才讨论从新发布物移除 OpenWorkbuddy 的署名。
3. **生态中零 MIT**：连 Electron、React、Pi 等第三方 MIT 组件也不用。这不是产品独立的必要条件，代价很高，不作为默认目标。

MIT 允许使用、修改、分发、再许可和商业销售，但要求在软件的副本或实质部分中保留原版权声明和许可声明。DeskForge 自己新增的代码可以有自己的版权和许可；已有公开发布的 MIT 版本不能通过后续修改追溯收回。选择闭源也不会消除所保留上游代码的署名义务。

## 当前事实和风险

- Git 历史 `7972bd6` 明确写着 “Port DeskForge P0 from OpenWorkbuddy”；当前仍以 Electron 主进程、renderer、agent-host 和 tool-runner、`contracts`、`core`、SQLite 为基础架构。
- 以 `7972bd6` 为基线，原有 113 个 `.ts/.tsx/.css` 源文件在当前路径仍存在；其中 67 个文件未发生 Git 内容变更，46 个已修改，并新增 57 个源文件。这是改动覆盖率线索，不是逐行版权判定。
- 已有明显的 DeskForge 自研增量：模型服务兼容、工作区搜索和审批 diff、Skill/MCP、本地知识库与会话搜索。但 `database.ts`、`tool-broker.ts`、`contracts`、`agent-host`、UI 等核心仍承接移植代码和设计。
- 根 `LICENSE` 只有 DeskForge 权利人；本轮已在 `licenses/OpenWorkbuddy.MIT.txt` 加入上游完整 MIT 文本并配置打包。仍需核对上游固定版本、真实安装包和第三方许可清单。
- 有残留上游命名：`update-service.ts` 读取 `WORKBUDDY_UPDATE_FEED_URL`，`run-preparation-pipeline.ts` 读取 `WORKBUDDY.md`，一个在线测试使用 `WORKBUDDY_ONLINE_SEARCH`。多处产品界面反复声明“不是 WorkBuddy”，反而持续强化关联。
- 输入框的“直接处理 / 先整理计划”是**任务执行方式**，不是授权档位。当前授权类型 `RunAccessMode` 只有 `approval`，界面中“工作区 · 请求批准”下拉框只有一个选项；数据库创建和读取也固定为 `approval`。`packages/core/src/policy.ts` 虽保留了 `cautious / balanced / autonomous` 的策略函数，主进程 `tool-broker.ts` 没有把它接到任务选择上。
- `@earendil-works/pi-agent-core`、`@earendil-works/pi-ai` 是独立的第三方运行时依赖。即使 OpenWorkbuddy 代码被全部替换，仍须单独管理这些依赖的许可证和升级风险。

## 过渡阶段：保护现有版本并准备重建

### 第 0 阶段：来源和发布合规，1 个 PR

本轮已建立初版 `docs/SOURCE_PROVENANCE.md`，并把 OpenWorkbuddy 的完整 MIT 文本加入旧版打包资源。上游精确 commit、逐文件来源复核、第三方许可清单和真实安装包检查仍待完成。

**改动**：

- 固定本次审查所依据的 OpenWorkbuddy 版本或 commit，建立 `docs/SOURCE_PROVENANCE.md`：逐模块登记“上游保留 / 已改写 / 自研新增 / 第三方依赖”。初始列表覆盖 `apps/desktop/src/main`、`workers`、`renderer`、`packages/core`、`packages/contracts`。
- 把上游原始 `LICENSE` 全文原样收入 `licenses/OpenWorkbuddy.MIT.txt`，在 `NOTICE` 明确它与 DeskForge 自己的 `LICENSE` 各自覆盖什么；由负责发布的人校对作者、年份和上游固定版本。不要仅把根 `LICENSE` 的权利人替换成自己后删除上游文本。
- 为直接依赖和实际打包进应用的依赖生成第三方许可清单，并确认 DMG/ZIP 内可访问 `NOTICE`、上游许可、第三方许可。把“打包产物包含许可文件”的检查纳入发布脚本/CI。
- 确定产品发布模式：继续 MIT、未来新贡献采用其它开源许可，或闭源。变更许可前先审查贡献者权利、历史发行版本和各依赖条件。

**验收**：从一个干净的发布包能找到上游完整 MIT 文本、DeskForge 许可和第三方清单；每个保留的上游模块在来源表中有记录。许可文本和署名经人工复核。

### 第 1 阶段：冻结旧版功能，仅处理必要维护

现有仓库保留为有来源声明的过渡版。只处理安全、许可、用户数据导出，以及用户明确提出且可局部验证的必要体验修复（如工作区内受限自动处理）；不在这套代码上做大规模模块重构。残留命名如 `WORKBUDDY_UPDATE_FEED_URL`、`WORKBUDDY.md` 和 UI 文案列入维护清单；若不会再次发行旧版，可不为这些文案专门投入开发。新程序从自己的产品规格重新定义名称、配置和行为。

**验收**：旧版能安全导出用户数据；修复不会删除必要的上游许可声明；新功能进入新代码库。

## 主线：发布物彻底不含 OpenWorkbuddy 代码

2026-10-06 后续确认：用户要求保持当前相同功能。最小纵向流程只是实施顺序，最终兼容范围不缩减。已开始执行，见 [重建状态](rebuild/STATUS.md)、[完整功能矩阵](rebuild/ACCEPTANCE.md) 与 `independent/`。以下“按需求补齐”以完整矩阵为最终门槛。

这是单独立项的重建工程，不是把现有文件逐个改名或机械改写。先完成过渡阶段的第 0 阶段，以它留下的来源证据为基线。现有仓库只作为旧版本维护和行为观察对象；新实现应从独立规格出发。

1. **写独立规格（第 1 个交付包）**：从目标用户、真实任务、公开协议和自己的黑盒验收测试描述目标；不要拿上游源码作为新实现模板。先写清安全边界、工具风险分级、数据格式、故障恢复。产物：`docs/rebuild/PRODUCT.md`、`ARCHITECTURE.md`、`ACCEPTANCE.md`。
2. **建立隔离的新代码库（第 2 个交付包）**：使用新仓库、新 Git 历史和新构建配置。新实现者只按独立规格、公开 API 文档及自写测试工作；旧仓库代码不复制过去。建立 `SOURCE_LEDGER.md`，逐个记录新文件的作者、参考文档、第三方依赖和评审结论。新旧代码不能通过复制、转译或逐行改写互相迁移。
3. **先完成最小纵向流程（第 3 个交付包）**：界面选择工作区 → 连接模型 → 只读检索与引用 → 请求一次需批准的文件写入 → 保存会话 → 失败恢复。每一步先写独立测试，再实现。暂不迁移浏览器控制、自动化、MCP、Skill、向量检索等扩展功能。
4. **补齐必要能力（第 4 个交付包）**：根据真实用户需求选择增加本地知识索引、MCP、Skill 等。按“独立规格 → 实现 → 契约/安全测试 → 来源记录”循环。避免以旧仓库文件列表为开发清单。
5. **数据迁移与并行验收（第 5 个交付包）**：旧版本只导出经文档定义的用户数据格式；新程序独立解析导入。优先支持工作区配置、会话和用户创建的资料，不迁移加密 Key 明文或旧审计链。以匿名化副本验证迁移，允许用户保留旧程序并回退。
6. **发布前来源审计（发布门槛）**：对源代码、图片、文案、构建产物、安装包、锁文件与第三方组件逐项核查；做相似片段比对，但不把“相似度低”当作唯一证据。确认没有保留上游的受保护表达后，才由专业法律人员评估是否可从**新发布物**移除其署名。Git 历史和已发行旧版本仍会记录真实来源。

**粗略规模**：这是数月级工程，核心风险在安全策略、数据兼容和来源证据；不能用“改写了多少百分比”作为完成标准。对旧仓库做渐进式替换，通常难以形成清晰的独立来源证据，因此推荐新仓库和新历史。

### 新程序的执行与授权设计

这两个选择应独立显示，不沿用旧程序的单选下拉框设计：

| 选择 | 含义 | 不改变的边界 |
| --- | --- | --- |
| 直接处理 | 收到任务后直接进入执行阶段 | 不等于自动批准工具操作 |
| 先整理计划 | 先输出可审阅计划，再开始执行 | 规划阶段只读 |
| 请求批准（默认） | 文件写入、命令、对外发送等按风险策略暂停确认 | 只读操作可自动进行 |
| 工作区内自动处理（可选，后续版本） | 仅自动放行明确可撤销的本地写入和严格验证命令 | 工作区外路径、删除、支付/发布/发送、敏感文件和凭据、未知命令仍拒绝或逐次批准 |

新程序 MVP 先交付“直接处理 + 请求批准”以及“先整理计划 + 请求批准”；这已经覆盖截图里两个控件的核心体验。自动处理档位必须等到策略、审计、回滚和端到端安全测试完成后再开放。验收样本至少覆盖授权工作区内写入、工作区外路径、删除、MCP 外发、敏感配置和未知 Shell 命令。

## 决策门槛

- **已选择**：未来新发布物不含 OpenWorkbuddy 代码与署名。以“新代码库 + 独立规格 + 来源台账 + 发布前审计”为主线；当前仓库处于过渡阶段，继续履行现有许可义务。
- **许可范围**：目标是去除 OpenWorkbuddy 的代码与相应署名，不自动意味着禁用 Electron、React、Pi 等第三方 MIT 软件。第三方许可按各自条款继续处理。
- **准备闭源发行**：先明确新贡献的许可、贡献者授权和第三方清单，再设计发布条款；原先公开的 MIT 版本及保留的上游部分仍按各自许可处理。
